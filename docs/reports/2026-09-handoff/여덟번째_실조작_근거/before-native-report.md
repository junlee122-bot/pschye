# 라온제나 여덟 번째 작업 묶음 검증보고서

2026-09-15 · 기존 여정의 입력·저장·진행 검증

**슬롯·재시도 사이의 늦은 입력과 이야기 화면의 Enter 충돌을 수정했다. 전체 28파일·374개 테스트, 타입 검사·린트·프로덕션 빌드가 통과했다. 실제 브라우저의 새 게임부터 첫 작전까지 연속 완주는 아직 미완료다.**

## 수정한 문제

- 슬롯을 바꾸거나 같은 슬롯에서 새 여정을 시작한 뒤, 이전 화면의 좌표·선택 입력이 현재 저장을 바꿀 수 있었다. 이야기 선택과 마을 이동·구출에 현재 슬롯·세대 확인을 추가했다.
- 구출의 같은 동작이 두 번 들어오거나 재시도 전 행동이 새 시도에 적용될 수 있었다. 시도·동작 번호를 대조해 오래된 입력을 무시한다. 실제 App에 이전 콜백을 전달하는 5개 검사가 수정 전 모두 실패했고 수정 후 모두 통과했다. 마을 표시 컴포넌트와 저장 I/O를 제어한 재현이며, 자연 발생한 Phaser 이벤트 경주를 관찰했다는 뜻은 아니다.
- 이야기 화면의 전역 Enter가 타이틀 버튼의 Enter에도 반응했다. 버튼·링크·편집 영역, 조합키·반복·IME 입력은 전역 단축키에서 제외했다. 제목·배경의 Enter와 숫자 선택은 유지했다.

원전·기존 이야기 데이터·정식 전투 및 성장 규칙은 변경하지 않았다. jsdom 26.1.0은 개발 의존성으로 추가했다.

## 자동 검사로 확인한 범위

기존 356개에서 **18개 증가해 374개**가 통과했다.

| 검사 | 수 | 확인 범위 |
|---|---:|---|
| 여정·전투 규칙 통합 | 6 | 세 성향의 서장·체험 진행과 매 행동 저장/복구, 4인·6인 첫 작전 6회 승리, 엔진이 만든 패배·재시도·포기·재출전, 저장 실패 때 마지막 저장 유지·재제출/재정산과 중복 보상 차단 |
| App 입력 격리 | 5 | 다른 슬롯·같은 슬롯 초기화의 이전 좌표/선택, 중복 구출 행동, 실제 동작 소진 뒤 재시도에 들어오는 이전 행동 |
| 이야기 키보드 DOM | 6 | 초점·버블링, 버튼/편집 영역/조합키 제외, 제목 단축키, 화면 해제 후 이벤트 정리 |
| 실제 App DOM 흐름 | 1 | 폐광 도중 재마운트 복구 → 마루 수련 → 카인·카즈린·하도리 → 후일담·선서·입단 → 첫 작전 방식 선택 |

마지막 흐름은 통찰 한 경로이며, 제품 화면·리듀서·저장을 모의 객체로 바꾸지 않고 IndexedDB가 없는 jsdom의 LocalStorage와 실제 save/load를 사용했다. 앞선 7장면의 완료 상태는 준비 시드다. [Vitest의 jsdom 환경](https://vitest.dev/guide/environment.html)은 DOM을 모사하므로 이 검사를 실제 Canvas 렌더링·물리 입력·새 게임 전체 완주로 세지 않는다.

규칙 통합의 저장은 Map 기반 localStorage 모의와 setItem 예외 주입을 사용했다. 승리 저장 실패 때 마지막 active 저장 유지 후 보유한 유효 승리 상태를 재제출했고, 정산 저장 실패 때는 저장된 승리를 다시 읽어 중복 없이 정산했다. 잃은 승리의 자동 복원을 확인했다는 뜻은 아니다. 규칙 API로 만든 승패도 브라우저 전투 조작과 구분한다.

TypeScript·전체 ESLint 및 추가 흐름 파일 ESLint·프로덕션 빌드·Git 공백 검사를 통과했다. 마을·수로·폐광·수련·조장 선발·정식 전투 청크를 유지했고, 테스트·제작자 전용 청크는 배포에 포함되지 않았다. 기존 Phaser 대형 청크 경고는 남아 있다.

## 실제 브라우저 결과

새 Edge의 가벼운 진단 화면에서 실제 마우스·Tab/Enter 입력과 화면 갱신을 확인했다. 이어 격리한 4407 저장 공간의 새 게임으로 마을과 390px 조작을 열었다. 이 여정은 **7묶음 커밋 1d07e4f의 배포본**이므로 이번 수정의 검증 근거로 사용하지 않는다.

게임에서 입력 시간 초과가 났지만 같은 탭·origin의 진단 페이지는 정상 작동했다. 게임에 재접속해 한 번 입력하고 다음 호출에서 읽는 방식으로 9개 이동·관찰 쌍을 확인했다. 10번째 입력 뒤 화면 읽기가 시간 초과되어 첫 대화 전에 중단했다. 이 대조만으로 원인을 앱·Phaser·저장 처리·도구 중 하나로 확정할 수 없다.

최종 소스의 별도 키보드 사례: 최종 수정의 실제 App에서 선택 완료 capital-gate의 타이틀 버튼을 Enter로 실행한 뒤 타이틀 이동과 실제 저장 불변을 확인했다. 입력 도구 timeout은 1회 복구 후 결과를 관찰했고, 320px 스크린샷은 후속 도구 timeout으로 미획득이다.

확인한 항목:

- 명시한 앞 5장면 준비 후 실제 chooseOriginStoryPath identify-poison으로 capital-gate 선택을 적용하고 실제 save/load가 준비 요약을 그대로 보존했다.
- 선택 완료 이야기의 타이틀 버튼에 실제 locator.press Enter를 실행했다. 도구는 timeout을 보고했으나 1회 getTab 후 실제 title URL/화면과 서장 6/영웅들의 그림자 아래 저장 슬롯을 확인했다.
- 이동 후 UI 검사 버튼이 호출한 실제 loadCampaignProfile 결과에서 currentSceneId=capital-gate, score 4, choices, completedSceneIds가 모두 불변이었다.
- 자원·성장·관계·로그 등을 포함한 전체 저장 요약도 Enter 전 실제 load 요약과 완전히 동일했다.

이 사례의 한계:

- Enter 입력 API가 Input.dispatchKeyEvent timeout 1312ms를 보고했다. 1회 getTab 복구 후 결과를 관찰했으며 Enter를 다시 누르지 않았다.
- 후속 fullPage 스크린샷에서 Page.captureScreenshot timeout 5000ms가 발생해 추가 캡처/재연결을 중단했다. 같은 호출의 metrics/log 조회는 실행되지 않았다.
- 앞 5장면과 capital-gate 선택은 실제 API를 쓴 명시적 준비다. 앞선 서장 플레이나 선택의 수동 실행으로 세지 않는다.
- 고유 4408 slot 1만 사용했다. 원본 사용자 storage/src/dist 변경이나 다른 브라우저 백엔드/rawCDP 우회는 없었다.

## 남은 검증과 다음 순서

- 새 게임 → 수로 귀환 확인 → 폐광·수련·세 대결 → 입단 → 첫 작전의 실제 연속 진행.
- 실제 화면에서 중간 저장·타이틀·재개, 슬롯 전환, 첫 정식 전투 승패·정산·재출전.
- 남은 성향별 직접 실패·재시도, 4인/6인 편성과 동료 명령, 320px의 주요 플레이 화면·터치 길게 누르기/취소.

이 항목들은 자동 검사 통과만으로 완료 처리하지 않는다. **8묶음의 실제 여정 검증을 마무리한 뒤 9묶음인 3D 조작 기반·라온으로 넘어간다.**

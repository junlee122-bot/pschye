# 라온제나를 젤다·붉은사막 수준으로 발전시키기 위한 제작 조사

조사일: 2026-09-15 · 현재 구현 기준: `2981276` · 대상: PC 싱글플레이 3D 액션 어드벤처

이 보고서는 Nintendo·펄어비스의 공개 개발 자료, Unity·Epic·Steam 공식 문서, 현재 저장소를 대조했다. 비교 작품을 이번에 직접 플레이하거나 성능을 계측한 보고서는 아니다. **공개 사실**, **현재 프로젝트에서 확인한 사실**, **라온제나에 대한 제작 제안**을 구분한다. 아래 팀·일정·예산·품질 기준의 제안 수치는 실제 젤다나 붉은사막의 제작비·생산성을 뜻하지 않는다.

## 1. 판단: 다음 단계는 ‘더 많은 설정’에서 ‘검증 가능한 플레이’로 이동하는 것

라온제나는 세계관과 이야기·전투 규칙을 실험할 웹 기반을 확보했고, Unity의 첫 조작 소스를 마련했다. 하지만 실제 3D 게임은 컴파일·플레이 검증부터 남아 있다. 지금 가장 필요한 결과물은 **라온으로 걷고, 적을 읽고, 환경을 이용하고, 선택한 결과를 안고 돌아오는 하나의 완결 구간**이다.

젤다의 탐험·상호작용 설계와 붉은사막의 시각적 밀도·액션·전체 분량을 동시에 목표로 하면, 여러 해에 걸친 전문 제작 조직과 자금 조달까지 포함하는 사업이 된다. 소규모로 출발한다면 먼저 독자적인 작은 게임에서 일부 경험의 품질을 높이고, 실제 제작 속도로 확장 가능성을 증명하는 경로가 적절하다.

| 목표 수준 | 의미 | 이번 프로젝트의 결정 |
|---|---|---|
| 경험의 핵심 | 움직임이 좋고, 세계 규칙을 이해해 스스로 해결하며, 선택이 남음 | 지금부터 작은 구역에서 증명할 목표 |
| 한 구간의 높은 완성도 | 캐릭터·환경·전투·오디오·UI·저장·성능이 같은 품질로 연결 | 30~40분 대표 구간의 목표 |
| 작품 전체의 동급 규모 | 넓은 지역, 다수 적·NPC·연출, 오랜 플레이 시간, 여러 플랫폼, 출시 후 지원 | 제작 조직·자금·양산 실적이 확보된 뒤 별도 승인할 목표 |

현재 상태를 AAA 대비 몇 퍼센트라고 표현할 근거는 없다. 파일 수, 모델 점수, 테스트 작성 수는 플레이 품질과 분량을 측정하는 동일 단위가 아니다.

## 2. 젤다에서 배울 것: 공용 규칙, 탐험의 이유, 끝까지 반복하는 검증

### 확인한 개발 사실

TOTK는 이미 완성된 BOTW의 세계를 의도적으로 이어받고 새로운 능력과 놀이를 확장한 속편이다. 세계 재사용이 엔진·물리 시스템을 그대로 유지했다는 뜻은 아니다. 처음부터 기반과 모든 자유 결합 시스템을 동시에 만든 사례로 해석하면 안 된다. [Nintendo 개발자 인터뷰 Part 1, 2023-05-09](https://www.nintendo.com/us/whatsnew/ask-the-developer-vol-9-the-legend-of-zelda-tears-of-the-kingdom-part-1/)

개발진은 능력과 세계의 결합을 강조했고, 많은 조합을 실제로 작동시키기 위해 디자이너와 프로그래머가 세부 조정을 했다고 설명한다. 붙는 모양과 소리 역시 조작 만족감에 기여했다. 자유도는 기능 버튼 하나를 추가한 결과로 끝나지 않았다. [Nintendo Part 4, 2023-05-09](https://www.nintendo.com/us/whatsnew/ask-the-developer-vol-9-the-legend-of-zelda-tears-of-the-kingdom-part-4/)

움직이지 않는 상자와 부술 수 없는 항아리를 외형으로 구분하는 등, 가능한 행동을 예측할 수 있는 표현 규칙도 만들었다. 아오누마는 디버깅하며 시작부터 엔딩까지 약 20회 플레이했다고 밝혔다. 이는 전 구간 검증의 사례이며 우리에게 20회가 충분하다는 기준은 아니다. [Nintendo Part 5, 2023-05-09](https://www.nintendo.com/us/whatsnew/ask-the-developer-vol-9-the-legend-of-zelda-tears-of-the-kingdom-part-5/)

공식 CEDEC 세션 소개는 BOTW의 필드 제작을 발견·호기심·이동 행동을 유도하는 설계로 설명한다. 제작 파이프라인은 여러 직종이 실제 게임 안에서 확인하고 후반의 변경도 수용하도록 구성했다. TOTK의 필드·QA 소개에는 초기부터의 QA 참여와 자동화·수작업의 협업이 명시돼 있다. 여기서는 공개 세션 소개를 근거로 삼았으며 비공개 강연 전체를 열람한 것은 아니다. [필드 설계, CEDEC 2017-08-31](https://cedec.cesa.or.jp/2017/session/GD/s59007c6395fd6.html), [파이프라인·TA, CEDEC 2017-08-31](https://cedec.cesa.or.jp/2017/session/PRD/s58eedbb3d91b9.html), [필드 제작·QA, CEDEC 2024-08-23](https://cedec.cesa.or.jp/2024/session/detail/s661ccb97c2589/)

### 라온제나에 적용할 판단

- **맵의 평가 단위는 면적보다 행동이다.** 전망점에서 무엇을 보고, 갈림길에서 무엇을 예상하고, 도착했을 때 무엇을 발견했는지를 기록한다.
- **능력 하나를 여러 상황에 연결한다.** 기존 로드맵의 자르기·밀기·기맥 읽기 중 하나를 골라 전투·탐험·퍼즐에서 같은 규칙으로 작동시킨다. 여기서 새로운 정사 능력을 확정하지 않는다.
- **해법의 자유에는 복구 규칙이 필요하다.** 필수 물체를 엉뚱한 곳에 밀거나 다른 순서로 진행해도 필수 진행이 막히지 않아야 한다.
- **같은 모양은 같은 기대를 만들어야 한다.** 움직임 가능·고정·잠금·파괴·사용 완료를 형태·재질·소리로 구별한다.
- **기획자와 아티스트도 플레이해야 한다.** 텍스트·모델·스크린샷 검수 외에 같은 실행 빌드로 이동과 실패·재시도를 확인한다.

## 3. 붉은사막에서 배울 것: 고밀도 표현을 지탱하는 제작 체계

### 확인한 제품·기술 사실

[Enhanced 안내](https://crimsondesert.pearlabyss.com/en-us/News/Notice/Detail?_boardNo=125), [2.02.00 패치](https://crimsondesert.pearlabyss.com/en-us/News/Notice/Detail?_boardNo=130), [Known Issues](https://crimsondesert.pearlabyss.com/en-us/News/Notice/Detail?_boardNo=68)

### 라온제나에 적용할 판단

사실적인 장면을 목표로 한다면 조형·텍스처 해상도에 더해 피부·눈·머리카락·의상·발 접지·움직임 전환·조명·음향이 함께 좋아져야 한다. 그 상태로 실제 전투와 카메라를 돌릴 때 프레임 예산도 지켜야 한다.

큰 팀이 병렬 작업하려면 지형 수정, 적 배치, 대사, 퀘스트 상태가 서로를 불필요하게 덮어쓰지 않아야 한다. 라온제나는 작은 마을부터 공간·콘텐츠·영속 상태를 분리하고 같은 ID로 연결하는 방식이 필요하다. 현재 단일 연습장 bootstrap은 조작 증명에 사용하고, 콘텐츠 양산의 최종 편집 체계로 고정하지 않는다.

자체 엔진·자체 모션캡처 센터 건설을 다음 단계로 삼을 이유는 없다. 먼저 상용 엔진과 외주·기존 도구로 한 구간의 품질과 수정 비용을 확인한다.

## 4. 현재 프로젝트의 실제 출발점

| 분야 | 확보된 것 | 아직 남은 것 |
|---|---|---|
| 세계관·이야기 | 원전, 정사 판정, 장기 각색·분기 원장 | 첫 3D 출시 분량과 공간 경험으로의 재구성 |
| 웹 규칙 실험 | 8묶음의 382개 검사와 핵심 실브라우저 여정·저장 검증 기록 | Unity 전투·저장·UI로의 구현 및 별도 검증 |
| 3D 조작 | 라온 이동·점프·카메라·충돌 소스, 연습 장면 | Unity 패키지 해결·컴파일·물리·실제 입력 검증 |
| 라온 모델 | 42,592삼각형·33관절·20모프·16클립, PNG 호환 파생본 | 수동 토폴로지·스키닝·표정·발 접지·재질·전투 동작 승인 |
| 자동 검사 | C# 구문·GUID 참조·픽셀/버퍼 보존, 테스트 34개 작성 | Unity EditMode 21·PlayMode 13 실행, 실제 플레이와 빌드 |
| 월드·NPC | 장기 설계 및 웹 표현 | 플레이 가능한 3D 마을·길·폐허, NPC 행동·상호작용 |
| 생산·출시 | Git 커밋, 실행 스크립트, 기초 자산 원장 | 새 PC 재현, 잠금 패키지, 자동 빌드, 작업 분업, 기기별 QA |

현재 `docs/FULL_JOURNEY_VERIFICATION.md`의 웹 검증 기록과 `docs/THIRD_PERSON_FOUNDATION.md`의 Unity 미검증 기록을 구별해야 한다. 이번 조사에서 웹 테스트를 다시 실행한 것은 아니다.

과거 캐릭터 보고서의 라온 85점·`verticalSlice` 분류에는 `engine=false`가 기록돼 있고, 원본 제작 보고서는 수동 리토폴로지 완료를 주장하지 않는다. 따라서 85점을 게임 완성도 85%로 읽으면 안 된다. 근거: `artifacts/3d/character-fidelity-report.json`, `artifacts/3d/blender/raon-production-v2.json`, `tools/3d/character-fidelity-audit.mjs`.

72개 주작전·144개 선택작전, 18대지역·60세부구역, 86에피소드·516장면은 서로 다른 계획 단위다. 합산해 제작 완료량으로 사용하지 않는다. **출시1 포함 / 후속 제작 / 설정 보존**을 구분하는 출시 범위 원장 하나가 필요하다. 원전과 기존 설정을 삭제하자는 제안은 아니다.

## 5. 먼저 증명할 게임: 30~40분의 라온 여정

기존 로드맵의 ‘마을→길→폐허→귀환’을 유지한다. 다음 표는 대표 구간의 제작 제안이며 최종 정사나 확정 일정이 아니다.

| 단계 | 체험 | 제작·검증 목적 |
|---|---|---|
| 마을 | 라온·주요 인물·당면 문제, 움직임과 대화 | 설정 설명 없이도 내가 왜 나가는지 이해 |
| 연결 길 | 전망점·갈림길·짧은 장애물 | 시선 유도, 이동 선택, 카메라·지형 검증 |
| 첫 전투 | 한 무기와 읽기 쉬운 적 | 예고→회피/흘리기→반격→피드백 연결 |
| 폐허 | 같은 환경 능력을 다른 상황에 응용 | 초기 두 해법부터 시험, 대표 구간은 기존 세 해법 목표·물체 유실 복구 |
| 선택 | 구출·기록·우회 등 기존 각색에 맞는 갈림 | 선택 결과가 상태·대사·공간에 정확히 반영 |
| 귀환 | 바뀐 인물·장소·다음 모험의 이유 | 완료·저장·종료·재실행까지 여정 완결 |

범위 상한은 직접 조작 캐릭터 라온 1명, 일반 적 2종과 미니보스 1종, 작은 환경 키트, 전투 3회·퍼즐 3개·주요 대화 6개·의미 있는 선택 2개로 둔다. 먼저 한 전투·한 퍼즐을 완성하고 이 상한까지 늘린다. 처음부터 이 숫자를 채우는 것보다 각 경험이 실제로 작동하는지가 우선이다.

## 6. 반드시 필요한 게임 시스템과 완료 판정

### P0 — 첫 대표 구간 전에 반드시 연결할 것

| 시스템 | 필요한 구체 작업 | 통과 증거 |
|---|---|---|
| 실행 기반 | 지정 Editor, 실제 패키지 해결, C# 컴파일, 장면 준비, 빌드 | 새 로컬의 깨끗한 클론에서 실행 성공, 로그·버전·커밋 기록 |
| 이동·카메라 | 가속·감속·회전, 턱·경사·점프·천장·낙하 복구, 벽·실내 카메라 | 30/60/120fps 조건에서 같은 경로와 실패 사례 재현·수정 |
| 입력 | 이동·보기·공격·회피·대화·메뉴 액션, 컨텍스트 우선순위 | 대화·메뉴에서 입력이 새지 않고 포커스/패드 복귀 후 고착 없음 |
| 액션 전투 | 입력 버퍼, 준비·유효 판정·회복 시간, 취소·무적 규칙, 적중 1회 보장 | 벽 뒤 타격·다중 콜라이더 중복 피해·사망 프레임·저fps 검사 |
| 적 AI | 감지·조사·추격·공격·경직·복귀, 경로 막힘 복구 | 적이 지형에서 영구 정지하지 않고 예고를 읽어 대응 가능 |
| 환경 반응 | 공용 상호작용, 대상 선택, 재질·고정·연결·잠금 상태 | 같은 종류의 물체가 장소에 관계없이 같은 규칙으로 반응 |
| 월드 상태 | 영속 ID, 퀘스트 단계, 문·NPC·아이템·선택 결과 | 선방문·역순·중간 귀환·재실행에도 모순과 진행 불능 없음 |
| 저장 | 버전, 원자적 쓰기·백업·손상 복구, 체크포인트, 중복 보상 방지 | 저장 중 종료·부분 파일·쓰기 실패·보상 전후 로드 검사 |
| 기본 피드백 | 타격/막기/헛침 소리, 공격 예고, 자막·조작 안내, 실패 이유 | 소리·색·애니메이션이 같은 상태를 알려주고 대사를 가리지 않음 |
| 성능·검수 | 대표 기기, 고정 경로, CPU/GPU·메모리·로딩 기록 | Editor 화면 외 실제 Player에서 최악 장면과 장시간 동작 확인 |

`AI Navigation` 같은 패키지는 경로 탐색 기능을 제공하지만 적의 판단·공격 타이밍·공정성을 대신 설계하지 않는다. 입력 재지정 역시 바인딩 변경뿐 아니라 저장·충돌 해결·기본값 복원이 필요하다. [Unity AI Navigation](https://docs.unity3d.com/6000.0/Documentation/Manual/com.unity.ai.navigation.html), [Input System 바인딩](https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/manual/ActionBindings.html)

### 작은 공용 규칙을 먼저 만드는 방법

예시로 자르기를 선택한다면 `절단 가능`, `고정`, `연결됨`, `퀘스트 보호`, `사용 완료` 상태를 먼저 정한다. 절단의 결과를 이동 경로 개방·물체 낙하·적 대응에 재사용한다. 중요한 물건은 사라졌을 때 돌아오거나 다른 경로를 제공하도록 한다. 모든 물체 위치를 영구 저장할 필요는 없지만 중요한 선택·보상·통로 상태는 저장돼야 한다.

| 같은 행동 | 탐험에서 | 퍼즐에서 | 전투에서 | 반드시 시험할 경계 |
|---|---|---|---|---|
| 자르기 예시 | 막힌 길 개방 | 연결물 분리·장치 작동 | 환경물을 이용한 전술 | 여러 번 입력·저장 후 재방문·필수 물체 유실 |
| 밀기 예시 | 장애물 이동 | 무게·위치 조건 변경 | 적과 물체의 공간 제어 | 경사·벽·끼임·구역 밖 이탈 |
| 기맥 읽기 예시 | 숨은 흔적 발견 | 장치 관계 파악 | 대응 단서 제공 | 미발견/발견 상태·필수 정보·색각 접근성 |

이는 기존 로드맵의 능력을 어떻게 시험할지 보여주는 설계 예시다. 각 기능의 정사 적합성과 실제 재미를 확인한 뒤 채택한다.

### P1 — 두 번째 지역을 만들기 전에 갖출 것

- **스트리밍:** 지역별 소유권, 비동기 로드·취소·해제, 공통 자산 수명, 순간이동·사망 귀환 처리. 30회 왕복 후 메모리가 지속 증가하지 않는지 측정한다.
- **NPC 생활:** 주요 NPC 소수부터 퀘스트·시간별 위치/행동/대사를 구현한다. 부재 중 대체 경로를 마련한다.
- **콘텐츠 편집:** 코드 복제 없이 대화·조건·보상·오브젝트 상태를 편집하고, 없는 ID·도달 불가능 조건·번역 누락을 검사한다.
- **장비·성장·경제:** 획득·소지 한도·장비 교체·소모·강화·스킬 해금·상점의 상태를 연결한다. 웹의 규칙을 참고하되 실시간 액션에서의 보상 속도와 난이도는 다시 검증한다. 첫 구간에는 작은 성장 한 번으로 충분하다.
- **모듈 환경:** 마을·폐허의 규격, 문·계단·지붕·소품 키트, 충돌·LOD·NavMesh·조명 규칙을 만든다.
- **연출:** 대화 카메라·시선·표정·자막·건너뛰기. 자연 종료와 건너뛰기가 같은 결과를 확정해야 한다.
- **접근성:** 입력 리맵, 감도·반전, 흔들림 조절, 자막 크기/배경, 색 이외의 신호, 설정 저장.
- **자동 빌드·QA:** 커밋별 컴파일·규칙 검사, 재현 세이브·로그 묶음, 이전 정상 빌드로 복귀, 실제 대상 PC 검사.

Addressables는 자산 관리·로드·해제를 지원한다. 참조 수명과 지역 상태의 제품 규칙은 직접 설계해야 한다. 패키지를 설치한 사실을 스트리밍 완료로 세지 않는다. [Addressables 개요](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/index.html), [메모리 관리](https://docs.unity3d.com/Packages/com.unity.addressables@2.7/manual/memory-assets.html)

P2에는 넓은 대륙, 다수 탈것, 자유 비행, 범용 등반, 복잡한 날씨·생태계, 대규모 군중, 다수 직접 조작 캐릭터를 둔다. 첫 여정의 재미를 증명하는 데 필요한 항목만 앞당긴다. MMO·공유 월드·실시간 AI 대화는 이번 싱글플레이 핵심 범위를 별도로 늘리는 결정이다.

## 7. 캐릭터·애니메이션·환경 아트에 필요한 실제 생산 과정

라온 하나를 다음 순서로 끝까지 제작해야 다른 캐릭터를 안정적으로 늘릴 수 있다.

1. **미술 기준:** 실루엣·체형·얼굴·의상·색·소재, 게임 카메라와 대화 거리에서의 목표를 확정한다.
2. **조형과 토폴로지:** 관절·얼굴 변형을 고려한 표면 구조를 정리하고 UV·재질 구역을 검수한다.
3. **리그와 스키닝:** 어깨·팔꿈치·손목·골반·무릎·목·얼굴, 무기 소켓, 극단 포즈와 의상 관통을 검사한다.
4. **동작 세트:** 시작·정지·급회전·옆걸음·경사·점프 시작/공중/착지·피격·사망, 이후 검술 동작을 연결한다.
5. **엔진 통합:** 이동 속도와 보폭, 발 접지, 공격 이벤트, 피격 판정, 레이어 전환, 카메라 거리의 얼굴 가독성을 맞춘다.
6. **품질·비용:** 게임 조명에서 피부·눈·머리카락·의상을 검수하고 LOD·텍스처·투명 오버드로·스키닝 비용을 측정한다.

현재 16개 클립을 보존한 사실은 이 동작 세트가 모두 자연스럽게 연결된다는 증거가 아니다. 라온의 수동 검수 승인 이후에 주요 조연·적의 제작 규칙을 복제한다.

전투 애니메이션에서는 실제 이동을 물리 모터가 결정할지, 동작의 루트 이동을 사용할지 역할을 정한다. 둘이 같은 이동을 중복 적용하면 미끄러짐과 판정 불일치가 생긴다. 자유 카메라·표적 고정·표적 전환, 상체 공격과 하체 이동, 높이가 다른 적과의 접촉도 한 무기의 범위에서 먼저 해결한다.

Motion Matching은 선택 가능한 도구이며 필수 조건은 아니다. Epic의 공식 구현도 검색할 애니메이션 데이터베이스를 요구한다. 도구 설치가 필요한 모션 데이터·접촉·전투 이벤트를 생성해 주는 것으로 해석하지 않는다. [Epic Motion Matching](https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-matching-in-unreal-engine)

환경 아트는 개별 모델을 많이 만드는 작업보다 **배치 규격과 반복 사용 가능한 키트**가 중요하다. 문 크기·계단 높이·벽 두께·재질·충돌·AI 경로를 정하고 두 번째 장소가 같은 규칙으로 만들어지는지 확인한다. 절차적 배치와 생성형 도구는 초안·변형·반복 배치를 돕고, 시선 유도·전투 공간·정사 일관성은 실제 장면에서 검수한다.

오디오는 발소리 재질, 이동 장비 소리, 적 예고, 공격·방어·헛침, 발견·귀환, 실내·실외 잔향과 음악 전환부터 연결한다. 모든 대사를 먼저 더빙하지 말고, 바뀔 가능성이 낮아진 주요 장면부터 녹음·현지화한다.

## 8. Unity를 계속 쓸 것인가, Unreal을 검토할 것인가

**현재 제안은 Unity 6 URP 기반을 실제로 실행해 첫 조작·전투를 확인하는 것이다.** 지금의 미검증을 엔진의 한계라고 판정할 자료는 없다. 사실적인 고사양 표현이 최우선으로 확정되면, 콘텐츠를 대량 제작하기 전에 렌더링 방향을 비교한다.

| 선택 | 맞는 출발점 | 추가 부담·확인할 것 |
|---|---|---|
| Unity URP 유지 | 현재 C# 기반, 스타일을 통제한 시각 표현, 다양한 PC 범위 | 고급 피부·머리카락·조명·월드 제작은 직접 통합·최적화 |
| Unity HDRP 검토 | Unity 경험을 유지하며 고사양 사실적 표현 지향 | 재질·조명·셰이더 변경, 장비·성능 목표 상향, 이행 검증 |
| Unreal 5 검토 | 고사양 PC/콘솔, 대규모 월드와 사실적 표현 중심, UE 경험 인력 확보 | C#/Unity 구현 재작성, 도구·자산 재검수, 새 빌드·협업 방식 학습 |

Unity 공식 문서는 URP의 확장성과 다양한 플랫폼, HDRP의 고사양 사실적 표현을 구분하고 뒤늦은 렌더 파이프라인 변경 비용을 경고한다. URP와 HDRP를 같은 프로젝트에서 동시에 사용하는 방식은 지원하지 않는다. [Unity 렌더 파이프라인 선택](https://docs.unity3d.com/6000.0/Documentation/Manual/choose-a-render-pipeline.html)

Unreal의 World Partition은 공간 셀과 스트리밍 소스로 큰 세계를 나누어 로드한다. 이것은 큰 공간을 관리하는 기반이며 재미있는 지역·퀘스트·저장을 자동으로 완성하는 기능은 아니다. [Epic World Partition](https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine)

엔진 비교를 한다면 같은 라온·작은 숲/마을·적 2종·대화 클로즈업으로 **초기 구축 시간, 한 번 고친 뒤 확인하는 시간, 캐릭터 품질, 빌드 프레임/메모리, 팀의 수정 가능성**을 비교한다. 기간을 1~2주로 제한하는 것은 평가 제안이며 완성품 제작 일정이 아니다. 결과로 하나를 선택하고 장기간 같은 게임을 두 엔진에 중복 구현하지 않는다.

웹의 정사·ID·선택 의미·보상 불변식·테스트 사례는 재사용할 수 있다. React UI·Phaser 장면·Unity C#이 다른 엔진에서 그대로 실행되는 것은 아니다. 저장 이전은 별도 데이터 계약과 마이그레이션 검사가 필요하다.

### 엔진 비용의 현재 공개 기준

2026-09-15 확인 기준, Unity Personal의 수익·자금 기준은 20만 달러이며, Pro는 연간 선결제 좌석당 2,310달러 또는 월 210달러로 안내된다. Runtime Fee는 취소됐다. Unreal의 일반 게임 라이선스는 제품의 평생 총매출 100만 달러 초과분에 기본 5% 로열티를 안내하고, Epic Games Store 매출에는 예외가 있다. 지역·계약·할인·적격 요건은 실제 도입 시 공식 조건으로 다시 확인한다. 이 요약은 계약별 최종 비용 산정이 아니다. 라이선스 비용만으로 엔진을 고르면 안 된다. 인력의 숙련도, 재작성, 자산 이행, 반복 작업 시간의 차이가 전체 예산에 큰 영향을 준다.

## 9. 장비: 다른 로컬을 선택할 때 확인할 것

현재 로컬에서 확인한 것은 i5-8250U, Intel UHD Graphics 620, RAM 약 7.84GiB, 조사 중 C 드라이브 여유 약 5.82GiB다. 공간은 수시로 변한다. Unity Editor는 알려진 경로에서 미발견이며, 다음 PC의 사양은 아직 확인되지 않았다.

Unity는 Editor 실행에 최소 8GB RAM을 권장한다. Epic의 현재 UE5 권장표는 32GB RAM·8GB 이상 그래픽 메모리를 명시한다. 이 수치는 엔진 사용 기준으로, 라온제나 완성품의 최소 사양이나 AAA 제작 여유를 보장하지 않는다. [Unity 시스템 요구](https://docs.unity3d.com/6000.0/Documentation/Manual/system-requirements.html), [Epic 하드웨어 요구](https://dev.epicgames.com/documentation/en-us/unreal-engine/hardware-and-software-specifications-for-unreal-engine)

**작업 장비 제안:** 3D 본 작업은 RAM 32GB 이상, 전용 GPU의 VRAM 8~12GB 이상, NVMe SSD와 수백 GB의 여유 공간을 출발점으로 잡는다. 고해상도 아트·무거운 장면 담당은 RAM 64GB·VRAM 12~16GB 이상의 여유를 검토한다. 정확한 제품 구매는 예산·현재 보유 장비·대표 장면 측정 후 결정한다. 특정 그래픽카드가 이 게임을 반드시 60fps로 실행한다는 보장은 아니다.

개발용 고성능 PC와 별도로 실제 지원하려는 중간/낮은 사양 PC에서 검사해야 한다. 캐시·원본 아트·버전 기록·빌드·백업을 둘 저장 공간도 필요하다. 현재 노트북은 문서·코드·웹 규칙 작업에 계속 쓸 수 있고, 사실적인 대형 3D 제작·성능 판단의 주 장비로 삼기에는 제약이 크다.

## 10. 필요한 인력과 책임

사람을 늘리기 전에 제작 책임을 정한다. 한 사람이 여러 직무를 맡을 수 있지만 각각의 결과물과 검수 책임은 남는다.

| 책임 | 구체적으로 끝내야 하는 일 |
|---|---|
| 디렉터·프로듀서 | 무엇을 만들고 뺄지 결정, 일정·비용·완료 기준, 플레이 결과에 따른 수정 |
| 게임플레이·전투 개발 | 입력·이동·카메라·전투·AI의 실행 품질 |
| 시스템·도구 개발 | 저장·퀘스트·상태·콘텐츠 도구·빌드·데이터 검증 |
| 레벨·퀘스트 설계 | 동선·발견·전투 공간·퍼즐·선택 결과를 플레이로 연결 |
| 캐릭터·테크니컬 아트 | 조형·재질·리그·스키닝·셰이더·LOD·성능 기준 |
| 애니메이션 | 이동·전투·접촉·표정·동작 전환, 필요 시 모션캡처 편집 |
| 환경·조명·VFX | 재사용 키트, 배치·라이팅·가독성·전투 이펙트 |
| UI·오디오·내러티브 | 읽히는 상태, 소리·음악·대화·연출·현지화 |
| QA·플레이테스트 | 재현·저장 경계·기기별 검사, 사용자 이해와 재미 관찰 |

소규모 대표 구간을 만드는 **12명 예시**는 디렉터/프로듀서 1, 개발 3, 레벨/퀘스트 2, 캐릭터/TA 1, 애니메이터 1, 환경 아티스트 2, UI/VFX 1, QA 1이다. 사운드·작곡·번역·특수 리깅 등은 별도 외주 또는 다른 역할의 일정으로 확보한다. 현재 이 인원이 있다는 뜻도, 정확히 이 숫자면 완성된다는 뜻도 아니다.

초기 보강 우선순위는 **실제 3D 게임을 끝까지 내본 게임플레이/기술 리드 → 라온의 변형을 책임질 TA·애니메이터 → 첫 구간의 레벨 설계 → 환경 제작 → QA·제작 운영**이다. 이미 보유한 역량에 따라 순서는 조정한다.

### 규모별로 가능한 계획의 차이 — 추정 시나리오

| 평균 전담 규모 | 우선 검토할 제품 범위 | 기간을 해석하는 방법 |
|---|---|---|
| 1~3명 | 한 능력·작은 지역의 실험, 잘 제한한 짧은 게임 | 수개월은 핵심 검증, 출시작은 수년이 될 수 있음. 대형 두 작품 전체 분량을 약속하기 어려움 |
| 8~15명 | 밀도 높은 대표 구간, 제한된 허브/지역 중심 작품 | 첫 고품질 대표 구간에 6~12개월 이상을 가정하고 실제 속도로 재산정 |
| 30~60명 | 여러 구역·적·연출을 양산하는 중형 액션 어드벤처 | 검증된 도구·리드·외주 체계 전제의 2~4년 계획을 검토 |
| 100명 이상+외주 | 큰 월드·고밀도 아트·다수 플랫폼의 대규모 사업 | 여러 해의 자금·경영·지원 조직 필요. 인원만으로 품질과 납기 보장 불가 |

이 표는 시장 평균 조사나 확정 견적이 아니다. 현재 유급 팀·예산·경험이 확인되지 않아, 범위를 정하기 위한 가설로 제시한다. 기존 ‘90일’ 로드맵은 작업 항목과 실험 순서로 활용하고 지금 상태에서 AAA급 완성을 약속하는 일정으로 사용하지 않는다.

## 11. 예산을 현실적으로 계산하는 방법

**기초 비용 = 평균 전담 인원 × 개월 수 × 1인 월 원가.** 인건비와 고용 부담·기본 운영을 포함하는 내부 계획 단가를 정하고, 외주·녹음·현지화·특수 장비·출시 지원·마케팅·예비비는 별도 견적을 합친다. 인력 증가와 감소는 월별로 계산해야 한다.

아래는 비용 규모를 이해하기 위한 계산 예시다. **업계 평균 단가도, 실제 젤다·붉은사막 개발비도, 라온제나 확정 견적도 아니다.** 급여를 받지 않는 개인 제작에서도 자신의 시간은 자원이며, 현금 지출과 구분해 기록한다.

| 가정 | 총 인월 | 가정한 1인 월 원가 | 기초 비용 계산 |
|---|---:|---:|---:|
| 3명 × 12개월 | 36 | 600만~1,000만 원 | 2.16억~3.6억 원 |
| 10명 × 18개월 | 180 | 700만~1,100만 원 | 12.6억~19.8억 원 |
| 30명 × 36개월 | 1,080 | 800만~1,300만 원 | 86.4억~140.4억 원 |
| 100명 × 48개월 | 4,800 | 900만~1,500만 원 | 432억~720억 원 |

가정의 크기가 다르므로 각 행을 동일 게임의 팀 규모만 바꾼 일정으로 비교하면 안 된다. 사람이 적다고 같은 전체 분량이 단순 비례해서 오래 걸리는 것만도 아니다. 전문성 부재와 병렬화 불가능 때문에 범위 자체를 바꿔야 할 수 있다.

다음 비용을 빠뜨리지 않는다: 자산 원본과 외주 수정, 모션/음성 녹음, 음악·효과음, 툴·엔진·저장소·CI, 테스트 장비, 현지화·LQA, 출시 심사·사업 운영, 트레일러·홍보·고객지원, 출시 후 패치와 예비 기간. 이미 월 원가에 넣은 항목은 다시 더하지 않는다.

첫 대표 구간에서 실제 투입 시간을 기록하면 비용 예측이 나아진다. 캐릭터 하나의 승인까지 수정 횟수, 적 하나의 전투 완성 시간, 퀘스트 하나의 검수 시간, 두 번째 구역의 제작 시간을 재어 다음 투자를 결정한다. 면적·자산 개수·AI 생성 속도로 예산을 계산하지 않는다.

## 12. AI·자동화가 도울 수 있는 부분과 사람이 책임질 부분

AI는 코드 초안·리팩터링·데이터 변환·참조 검사·회귀 사례·문서·에셋 분류·반복 배치를 도울 수 있다. 자동 빌드와 로그 정리도 반복 비용을 낮춘다. 그러나 현재의 도구 호출 속도를 애니메이터·레벨 디자이너·QA 전체 생산성의 고정 배수로 환산할 근거는 없다.

실제로 남는 책임은 재미와 난이도 판단, 조형·표정·관절의 수동 승인, 공격 읽기와 실패의 납득 가능성, 긴 구간의 페이싱, 원전과 플레이의 조화, 출시 품질의 최종 판단이다. 생성된 결과는 버전·출처·수정·검수 상태와 연결한다. AI를 많이 쓰더라도 책임자가 없는 영역을 ‘자동 완료’로 처리하지 않는다.

Steam의 현재 Content Survey는 일반적인 개발 효율 도구 사용과 플레이어가 소비하는 출시 콘텐츠를 구분하며, 생성형 AI로 만든 아트·소리·이야기·현지화 등의 사용을 다룬다. 실시간 생성은 별도 요구가 있다. 출시할 자산의 출처·사용 권한·제작 방법을 원장에 남기고 실제 내용에 맞게 제출한다. [Steam 공식 Content Survey](https://partner.steamgames.com/doc/gettingstarted/contentsurvey?l=english)

## 13. ‘이 정도면 다음 단계’라고 판정할 실제 기준

아래 수치는 **첫 실측으로 보정할 제안**이다. 비교 작품의 내부 QA 기준을 공개한 표가 아니다.

| 관문 | 제안 기준 | 실패하면 할 일 |
|---|---|---|
| G0 실행 | 새 PC 클론, 컴파일·34테스트·Windows 빌드, 모델·입력 확인 | 9묶음 결함부터 수정 |
| G1 조작·전투 | 동일 경로 반복, 적 예고·방어·피격·재시도 설명 가능, 치명적 조작 오류 없음 | 수치·카메라·동작·판정 재설계 |
| G2 첫 여정 | 개발자 설명 없이 5~10명이 핵심 목적·귀환 결과를 이해하는지 관찰 | 길 찾기·피드백·정보 순서 수정 |
| G3 데이터 | 보상 경계·역순 진행·손상 저장·구역 왕복·재실행에서 진행 보존 | 상태 소유권·저장 규칙 수정 |
| G4 성능 | 정한 PC·설정에서 CPU/GPU·메모리·로딩을 측정, 반복 시 누적 악화 없음 | 최악 장면 프로파일 후 자산/연산 예산 조정 |
| G5 생산성 | 두 번째 구역을 공용 도구로 제작, 작업·수정·검수 시간을 기록 | 양산을 멈추고 키트·편집기·역할 개선 |
| G6 출시 | 대상 기기·입력·언어·저장 이전·중단 복구·스토어 자료와 실제 빌드 일치 | 출시 후보 보류, 재현 가능한 수정 |

60fps를 목표로 정하면 한 프레임은 약 16.67ms다. CPU와 GPU 시간은 서로 겹칠 수 있으므로 단순히 더해 프레임 시간을 산정하지 않는다. 평균 FPS만 보지 말고 느린 프레임 분포, 처음 효과가 나올 때의 정지, 메모리 증가, 빠른 이동·전투·비·야간 등 무거운 조합을 측정한다. 목표 기기의 실제 Player 측정이 중요하다. [Unity 성능 데이터 수집](https://docs.unity3d.com/6000.0/Documentation/Manual/profiling-collect-data-introduction.html)

매번 모든 조합을 사람이 다시 해보는 대신, 상태 전이·저장·콘텐츠 참조는 자동 검사하고 이동·전투·아트·오디오는 실플레이와 관찰을 결합한다. 모든 버그를 제거했다는 주장 대신 심각도·재현·수정·회귀 결과를 관리한다.

## 14. 실행 순서: 다음 90일은 기반과 대표 구간의 가능성을 검증

기준은 숙련된 소규모 전담팀과 적절한 장비를 확보한 경우의 가설이다. 1인 또는 비전담 환경이면 기간보다 아래 관문 순서를 유지한다.

| 구간 | 주 작업 | 확인할 산출물 |
|---|---|---|
| 첫 1주 | 다른 PC 복원, Unity 설치/경로, 컴파일·테스트·빌드 | G0 로그, 플레이 영상, 실제 packages-lock, 결함 목록 |
| 2~4주 | 라온 입력·카메라·동작, 한 무기·한 적의 전투 | 60초 전투 반복판, 수동 승인한 캐릭터 기준 포즈 |
| 5~8주 | 작은 길·공용 환경 행동·퀘스트·저장·귀환 | 짧은 완주 가능 구간, 상태/보상/저장 회귀 검사 |
| 9~12주 | 대표 구간 연결, 아트·음향 피드백, 외부 관찰·성능 측정 | 임시 아트/회색 모형으로 30~40분 첫 플레이 구간 목표의 도달 여부·범위 재산정 |

90일 표의 산출물은 임시 아트를 포함한 첫 플레이 가능 구간이다. 10절의 6~12개월 이상 가정은 아트·애니메이션·오디오까지 다듬은 고품질 대표 구간으로, 서로 다른 목표다. 90일 안에 모든 최종 아트·다수 플랫폼·전체 분량을 완성한다는 계획은 아니다. 캐릭터 제작이나 전투 재설계가 오래 걸리면 목표 구간을 줄여 핵심 경험을 먼저 완결한다.

현재 ‘10묶음’은 이 조사에 따라 **10A 한 전투 → 10B 환경 행동·월드 상태·저장 → 10C 첫 왕복 여정 → 10D 외부 플레이테스트**처럼 검증 가능한 단위로 나눌 수 있다. 이는 후속 실행 제안이며 이번 요청에서 게임 기능을 추가 구현하지 않았다. 9묶음 G0가 먼저다.

## 15. 출시와 장기 운영에 추가로 필요한 것

PC판부터 입력 설정·언어·자막·세이브 경로·클라우드 동기화 충돌·창 전환·중단 복구·오류 로그를 제품 기능으로 관리한다. 접근성은 마지막 옵션 목록으로 붙이기보다 UI·소리·색·조작 설계에 포함한다. [Steam 접근성 기능 안내](https://partner.steamgames.com/doc/accessibility_features)

콘솔은 별도 개발자 등록·플랫폼 도구·실기 검증이 필요하다. 예를 들어 Unity의 Xbox 안내는 Pro, Xbox 개발자 등록, GDK·플랫폼 추가 도구를 명시한다. PC 실행 파일이 만들어졌다는 사실로 콘솔 출시 준비를 완료했다고 보지 않는다. 세부 심사 기준은 대상 플랫폼의 승인된 문서로 확인해야 한다. [Unity Xbox 개발 안내](https://unity.com/solutions/xbox)

유료 출시 전에는 지원 플랫폼과 사양, 플레이 시간과 포함 콘텐츠, 자산·음원·폰트·음성의 사용 권한, 연령/콘텐츠 정보, 테스트·고객지원·패치 예산을 확정한다. 이 조사에서는 출시 계정 생성·결제·계약·플랫폼 신청을 진행하지 않았다.

## 16. 다음 로컬에 전달할 작업 지시

> 저장소를 최신 main으로 받아 docs/THIRD_PERSON_FOUNDATION.md, unity/PsycheAdventure/README.md, docs/AAA_PRODUCTION_RESEARCH.md를 읽어라. 9묶음은 소스 준비 상태이며 Unity 실행 검증은 아직 통과하지 않았다. Unity 6000.0.75f1에서 실제 패키지 해결·Verify·EditMode·PlayMode·Windows 빌드·실조작을 수행하고 로그와 결과를 기록하라. 과거 캐릭터 점수나 웹 테스트를 Unity 완료 근거로 사용하지 말라. 첫 관문 통과 뒤에는 라온 한 무기·한 적의 전투와 공용 환경 행동, 마을→길→폐허→귀환을 작은 단위로 완성하라. 엔진 전환이나 전체 규모 확대는 대표 장면과 제작 속도 근거를 갖춘 뒤 판단하라.

## 17. 조사에서 확정하지 않은 것

- BOTW·TOTK·붉은사막의 최종 총개발비, 모든 외주 포함 인원, 정확한 프로젝트별 총인월은 이번 1차 자료만으로 확정하지 않았다.
- 엔진 시연·공식 마케팅 문구를 실제 모든 기기의 프레임·품질 보장으로 사용하지 않았다.
- Nintendo·펄어비스의 비공개 엔진 소스, 전체 GDC 강연, 플랫폼 비공개 인증 문서를 본 것처럼 기술하지 않았다.
- 현재 프로젝트의 실행 가능한 Unity 빌드·실제 모델 변형·조작감·성능은 여전히 검증 대기다.
- 사용자의 유급 전담 인력·예산·목표 출시일·새 PC 사양이 미확인이다. 이 네 가지와 첫 대표 구간의 실제 생산성이 확보되면 위 시나리오를 실행 견적으로 좁힐 수 있다.

이 보고서의 우선순위는 **검증되는 조작 → 한 전투와 한 공용 행동 → 선택과 저장이 남는 첫 여정 → 아트·오디오·성능 통합 → 두 번째 구역 생산성 → 전체 범위와 투자 결정**이다.
